# Connected Native Desktop Qualification

Cycle308 connects the existing launch-desktop profile to the complete input and
lifetime qualification routes. The kernel and application authorities are not
expanded. Actual passing receipts, not this description, determine qualification.

## Explicit Profiles

`native_app_session.profile_options` accepts only boolean receipt flags.
A launch console requires its launch shell, and that shell requires optical
file waits, window surfaces, capacity, generation-bound lifecycle and isolated
input. Diagnostic/serial-fault profiles are not ordinary previews. Ordinary
four-page shell accounting stays unchanged; a five-page shell requires the
explicit launch profile in both positive and hostile marker validation.

The adapter is shared by receipt admission, QEMU/VirtualBox launchers, local
keyboard, window/application-input, lifetime and GUI qualifiers. Native source
bindings, artifact hashes, optical inspection and complete marker checks remain
independent requirements. Receipt flags are not cryptographic authentication.

Each direct launcher/qualifier preflights storage before output creation.
Owned disposable VMs have no guest network, host shares, physical disks or
physical-media writes. Preserve all prior evidence and preview dependencies.

Before freezing execution sources, run the capacity and surface-lifecycle
structural tests alongside the launch-admission, ISO, VirtualBox/mouse, local
console, windows, application-input and input-lifetime modules. Do not defer
these source-bound structural guards to the later roadmap suite. The first
Cycle308 cohort had to be repeated after that omission exposed two stale
inline-keyword assertions; all original evidence remains preserved.

## Device And Lifetime Matrix

- GUI: mouse and function-key launches; held F3 repeats must not launch again
  or refocus the new application; release precedes inspection. Four pending
  terminal drafts and both application restarts must remain exact.
- Application input: normal and bounded four-byte bursts, mouse focus, drag,
  minimize/restore, independent Text/Numbers drafts, results, overflow/recovery,
  held key/modifier quarantine and six generation/lifecycle pixel barriers.
- Lifetime: active focused drag at fault/stop, held modifier suppression,
  explicit focus recovery, no input delivery to a retired generation, and
  exact permitted serial fault/stop controls separated from keyboard input.
- Launchers: exact application-session self-tests through both public entry
  points, including file work, retirement, sustained progress and cleanup.

Run the device matrix on QEMU and the pinned VirtualBox runtime. Headless runs
verify rendered guest pixels and emulated device paths, not a physical keyboard
or human interaction with the host VM window. F12 is the neutral typematic
control, outside the desktop's F1-F3 commands. VirtualBox capture permissions
extend only to bounded `launch-000.ppm` through `launch-191.ppm` names in the
owned work directory; arbitrary paths and larger indices still reject.
The held-repeat result is scoped to these injected emulator gestures. It does
not establish continuous physical typematic delivery: a backend can filter
duplicate make events before the guest receives them.

## Preview Boundary

A replacement preview requires a passing current-source optical baseline,
both backend input/lifetime modes, GUI and launcher evidence, exact ISO bytes
and unchanged source after execution. Preserve the historical Cycle303 pointer
until all required evidence passes. Copy a new `.iso` without overwriting old
downloads, and verify the copy byte-for-byte. The launchers must admit the new
receipt with ordinary checks, not rewritten historical receipts.

## Connected Desktop Controls

In a qualified launch-desktop session, click Text or Numbers on the bottom
taskbar to start a missing application. F2 and F3 perform the equivalent action;
F1 selects Terminal. An existing surface is shown/focused instead of spawning
another process. A newly admitted application does not steal the unfinished
terminal draft; click its window when ready to type.

Shift+F2 and Shift+F3 inspect the respective process through the shell-owned
control service without injecting a terminal command. The top status is the
last control result; the separate surface label comes from the window lifecycle.
An admission acknowledgment alone does not prove that a surface exists.
Release a held activation key before making another request.

Drag a title bar to move its window. The minus control minimizes it; its taskbar
entry restores it. Minimizing does not stop the process. Terminal `stop` and
`fault` commands still exercise explicit lifecycle paths; starting again creates
a fresh application generation, not a resurrection of retired scratch state.
Text and Numbers retain their existing bounded scratch-input/file workflows,
not persistent document editing.

This is a bounded development desktop with two applications and bundled files,
not a production desktop or installer. Persistence, compositor restart,
standalone COM2-independent startup, event-driven idle, native stale/delayed/
failed-launch controls, right-click native inspection, complete stack bounds,
physical hardware, accessible PooleGlass, PooleGlyph/PDC and all N0-N39 gates
remain required. No main merge, signing or release promotion follows automatically.

The standalone-startup gap is concrete: `native/userspace/src/bin/launch_console.rs`
configures the UART before starting the window service, and the `Registers`
implementation in `native/userspace/src/process/windows.rs` forwards terminal
reads/writes to serial before completing local rendering. A future local-only
profile must separate optional diagnostic-device absence from revoked or invalid
capability transport. Do not swallow authority failures, enlarge port grants,
or present missing diagnostic observations as native success.
