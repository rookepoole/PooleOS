# Native PKSMP5 Multi-AP Runtime And Shootdown

PKSMP5 scales the bounded PKSMP1/2/4 path to one exact four-vCPU `SandyBridge,-avx` QEMU topology: BSP APIC ID 0 and legacy-xAPIC application processors 1, 2, and 3. Each AP owns a private 32-page below-1-MiB runtime, page-table root, guarded stacks, descriptors, IDT, xstate page, APIC mapping table, request/response mailbox, and two shootdown frames. Local CPU masks are derived as `1 << APIC ID`, producing `0x2`, `0x4`, and `0x8`; the aggregate target and acknowledgement mask is `0xE`.

The first startup attempt deliberately starts APs 1 and 2, targets absent APIC ID 4, and reaches one bounded timeout. The BSP final-INIT parks the two started APs, revokes aliases, scrubs and read-verifies all first-attempt runtime and frame pages, releases all three allocated resource sets, and requires fresh allocations before retry. The second attempt brings all three APs online simultaneously and revalidates their private GDT/TSS/IDT, guarded-stack, x87/SSE, and APIC-table state.

The current implementation records attempted real-AP starts before issuing
startup commands. A missing online acknowledgement therefore cannot cause a
possibly started AP to be omitted from final parking. The deliberately absent
APIC-4 target remains a frozen-topology negative case, not general discovery.

Each online AP receives one valid diagnostic request, one forged-capability denial, one generation-bound shootdown request, and one stop request. The AP-side trampoline validates the fixed development capability, vector, sequence, attempt, root, page, generations, frames, local mask, and checksum before executing exactly one `INVLPG` for virtual page `0x001FF000`. Three private acknowledgements are validated independently and folded into aggregate mask `0xE`; reclaim is rejected twice before all unique acknowledgements arrive. Those acknowledgements permit the generation-retirement decision, not immediate physical-frame release. PKRETAIN1 tokens keep old frames held through stop acknowledgements and final INIT parking of every started AP. Only after that boundary may the BSP scrub and read-verify retained frames and runtime regions. Owner-authorized PMM release ends retention at allocator commit; failed scrubbing returns ownership for retry.

The successful lifecycle records nine accepted and three denied deliveries, twelve EOIs, three remote invalidations, three stopped/quiesced APs, final INIT parking, capability and alias revocation, and exact release of 96 runtime pages plus six frames. Both the partial attempt and successful attempt verify 417,792 bytes. Resource receipts permit allocator metadata-growth gaps but require every allocation and release sequence to be positive, unique, non-aliased, and causally ordered.

The linked-image audit requires exactly one `INVLPG (%rax)` instruction inside `poole_ap_ipi_trampoline_start..poole_ap_ipi_trampoline_end`; runtime execution count is three. The same linked scope contains a separate `INVLPG (%rbx)` for the successor lock profile, which PKSMP5 does not execute. Source controls require dynamic APIC-derived local masks, the multi-AP coordinator, explicit panic/stop counter bindings matching the frozen wire layout, and no arbitrary callback. The ordered aggregate root/frame receipts use domain-separated FNV-1a folds and cannot silently cancel to zero.

Qualification is generated by `python tools/qualify_native_kernel_smp_ipi.py`. It requires all 246 current kernel host tests, two fresh exact four-vCPU QEMU runs, 40 markers per run, exact screenshots and PBP1 bytes, independent lifecycle/transport/shootdown/resource models, a linked instruction audit, and 33 negative-control groups covering 609 rejected cases. The readiness artifact retains only the bounded `FLAG-N8-SMP-MULTI-AP-001` closure and predecessor bounded IPI/shootdown closures.

Cycle 191 checks strict recorded run IDs/counts/exits, raw digests, typed parsed
summaries, profile, handoff/revalidation bindings, channel agreement, normalized
static markers and frames. Complete aggregate observations and summary values
must match parsed records. Each negative-control category has its own bound count.
The three release-accounting controls call the same checked accounting function
used by the marker parser, not assertions over unequal constants. Aggregate old
and new frame checksums are recomputed for the frozen contiguous private-frame
layout with separate domain tags; arbitrary allocator layouts are not claimed.

## PKMBX1 Saved Mailbox Evidence

The explicit `PKMBX1` extension replaces the old opaque-checksum admission.
Each AP marker carries `mailbox_evidence=PKMBX1 snapshot=quiesced`, five BSP
context words, all 15 baseline checksum words, and all 38 runtime checksum
words. The contract freezes their order and native u32/u64 widths. Encoding is
comma-separated `0x` plus exactly 16 uppercase hexadecimal digits per word;
checksum input is each u64's eight little-endian bytes, folded with FNV-1a64.
The transport/capability contract stays PKSMP5; older markers without PKMBX1
cannot qualify the new implementation.

PooleKernel captures the BSP feature/timing context and quiesced AP snapshots
before final INIT and resource release. Logging reads only these saved values,
not freed AP memory. The independent Python oracle checks both checksums,
cross-checks AP/BSP identity and features, reconstructs private descriptors and
stack/xstate addresses, and checks control state, selectors, vector ownership,
fault state, xstate ownership/round trip and BSP-bounded AP timestamps. Every AP
must report the same BSP context. Only validated timestamps and their dependent
checksum words are normalized between runs; all other exported words stay exact.

Each AP adds 120 raw-parser rejection executions: 58 coherently invalid semantic
words, 53 checksum-input corruptions without resealing, and nine malformed
version/phase/shape/order cases. Unit tests additionally cover width overflow,
cross-AP substitution and frozen Rust/Python vectors. These are consistency and
bounded invariant checks, not cryptographic authentication or proof that every
possible internally consistent forged transcript can be detected. Current-source
fresh boot receipts are still required; source implementation alone does not
establish execution, close N36 or promote production.

## Execution Resource Ownership

Cycle 171 binds readiness to the exact current PKXFER1 receipt and the six
regenerated canonical boot artifacts. Both transfer runs must parse, agree,
and match the current retained-artifact digest. Each SMP run must then match
that current nine-file revalidation observation, including policy/state hashes.
Relabeling old evidence with new source hashes or consistently replacing its
recorded boot digests cannot satisfy this check. Malformed dependency objects
return validation errors, and regenerated artifact-byte drift is rejected.
This is dependency and record
consistency validation, not authentication or closure of the broader N36 audit.

The qualifier validates the JSON-serialized receipt before writing it. Each
stored run and the aggregate observation must agree with independent marker
parsing; receipt-sequence arrays retain the same types after a JSON round trip.
The release gate also binds the embedded kernel image and ownership counters.

Cycle 167 extends the actual AP path with `PKAPOWN1`: mandatory atomic retention
of each runtime allocation and both data frames. All possible shared CPU users
are recorded before startup. Copied handles cannot release retained regions;
owner-authorized scrubbed release cannot start while execution is possible.
Failed scrubbing keeps ownership for cleanup retry, and owner loss retains pages.

The partial-start and full-start attempts each exercise 27 copied-handle free
denials and 18 owner-release denials. Each successful denial leaves PMM summary,
physical-access counters and ownership state unchanged. Both marker records must
contain the exact observed counts; recorded run summaries and the aggregate
observation must agree with independently parsed markers. These are consistency
checks, not authentication or general hardware-quiescence proof.

The final INIT sequence remains an unsafe platform boundary. Intel describes
an AP entering wait-for-SIPI after INIT and requires interrupt inhibition during
MP initialization. The existing code is qualified only against the declared
QEMU topology; this does not establish those platform conditions for physical
targets or provide a general CPU-offline protocol. See Intel SDM Volume 3A,
sections 10.4.2 and 12.4.7.3 in the
[consulted edition](https://cdrdv2-public.intel.com/835754/253668-sdm-vol-3a.pdf).

General task execution-stack lifetime, CPU retirement, hotplug and broad live
fault/interleaving coverage remain open under N12.3. A current-source passing
receipt is required before claiming this candidate's bounded live evidence.

The historical Cycle 157 replay candidate was the Cycle 153 retention-capable
kernel, 517,784 canonical bytes in a 144-page image, SHA-256
`BDEECCB27B1B91406911F91169B9BF5F9DF0439BB39FA0E1882C07E1AF3B81EF`.
Exact-source replay is required. Source-bound lifecycle observations are not
the independent retirement/failure oracle or mandatory all-task/root/frame
ownership integration still required by N12.3.

PKSMP5 is not a general SMP or shootdown subsystem. It does not claim arbitrary topology, x2APIC, hotplug, NUMA, multiple sockets, address-space-wide invalidation, concurrent generations, INVPCID/PCID, scheduler ownership, migration or affinity authority, production capability minting, every failure interleaving, physical-target evidence, or user, PGVM2, PDC, or PooleGlyph dispatch. It does not close N8, N9, a release gate, or production readiness.
